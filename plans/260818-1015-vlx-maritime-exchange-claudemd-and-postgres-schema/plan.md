# VLX Maritime Exchange — CLAUDE.md and Postgres Schema

## Overview

`ui-2.html` (4,958 lines, 546KB) is a complete, self-contained HTML prototype of **VLX** — a Vietnamese maritime trading & maritime-finance exchange (VMFB programme). It carries 6 personas, 38 routed pages, and ~50 distinct in-memory data collections generated by a seeded PRNG.

> **Source file:** `ui-2.html` supersedes the original `ui.html` as of 2026-08-18 (see Validation Log — Session 2). All line citations in this plan refer to **`ui-2.html`**. `ui.html` remains in the repo but is no longer the contract.

This plan turns that prototype into two durable artifacts:

1. **`CLAUDE.md`** — repo instructions so future sessions understand the domain, stack, and conventions without re-reading 546KB of HTML.
2. **A complete Postgres schema** — Drizzle ORM definitions, migrations, and a deterministic seed that reproduces the prototype's dataset exactly.

**Not in scope:** building the Next.js app, porting UI pages, or any API/route work. Tooling added is the minimum needed to run Drizzle (`package.json`, `tsconfig.json`, `drizzle.config.ts`).

## Risks

| ID | Risk | Impact | Mitigation |
|---|---|---|---|
| R1 | **No auth ⇒ no data boundaries.** The prototype shows `boundary()` / `cdpBoundary()` notices claiming member-scoped data walls (CDP 360, neutrality pages). With no auth these are decorative — every row is readable. | **Accepted** — demo only | User accepted in validation session 1: this build is for demonstration, universal read access is fine. All data is synthetic (PRNG-generated), so no real customer records are exposed. Still keep `member_id` FKs on scoped tables so row-level scoping can be added later without migration. |
| R2 | **Shared PRNG stream.** All generators draw from one LCG (`_s=987654321`, seed at line 652). Any change to generation *order* silently changes every downstream dataset. | High — **empirically demonstrated** | The `ui.html` → `ui-2.html` edit proved this live: enlarging `OFFERS` (108→320, more fields per row) left `MEMBERS` and `SHIPMENTS` byte-identical (they draw *before* offers) but shifted every collection *after* it — `RFQS[0].bids` went 15→11 and `DOCS[0]` went `EBL-2026-4002`→`DOC-2026-4000`, with `BIDS` total moving 708→671. Port generators in exact source order; assert row counts and a content checksum in Phase 7. |
| R3 | **Ambiguous units.** The prototype mixes USD/TEU, `tỷ đồng`, `triệu USD`, and unscaled integers (`members.limit` is `ri(30,60)*1000` with no stated unit). | Medium | Phase 1 resolves each by reading the render site, not the generator. Unresolved cases become explicit open questions, not guesses. |
| R4 | **Bilingual free text in generators.** Issue types, AML types, agent actions, RFQ scopes are inline `[vi,en]` tuples inside loops. | Medium | Promote each to a reference table in Phase 3; transaction rows store the FK. |
| R5 | **Prototype has no timestamps/audit.** Dates are day-offsets from a hardcoded anchor `new Date(2026,7,15)` = 2026-08-15. | Low | Store real `date` columns anchored to 2026-08-15; add `created_at`/`updated_at` defaults on all tables. |
| R6 | Scope creep into building the app. | Medium | Phases 3–7 touch only `db/`, config files, and `docs/`. No `app/`, no `components/`. |

#### Method change: the seed executes the prototype instead of re-implementing it

Phase 6 assumed a hand-port of the 23 generators, with the PRNG contract and draw order as the dominant risk (R2). That was replaced: `db/tools/prototype-data.ts` runs `ui-2.html`'s own script in a `node:vm` with a stub DOM and reads the resulting arrays.

This removes R2 entirely — the seed cannot drift from the prototype because it *is* the prototype — and deletes the eager-evaluation and second-pass `depN` traps as concerns rather than mitigating them. Bilingual labels are recovered by running the script twice (`LANG='vi'` / `'en'`) and pairing by row index; verified that row identity holds across both passes. The same approach was applied to CSS (`db/tools/extract-css.mjs`), so the design system cannot drift either.

Two guarded modifications to the extracted script: `dstr`/`dshort` rewritten to emit ISO dates (neither touches the PRNG), and everything after the bootstrap marker cut so page functions stay defined but never run. Both assert on mismatch.

#### Correction to this plan: `status_labels` is not universal

Phase 3 recorded that `ST_TAGS` has no duplicate codes and concluded one shared dictionary was safe. Verification against a real database disproved the conclusion — the check had confirmed uniqueness *within* `ST_TAGS`, not across domains.

`PR_ST` (ui-2.html:3104) reuses the code `live` to mean "Đang niêm yết / Listed" where the shared dictionary means "Đang mở / Open". `products.status_code` therefore points at a separate `product_statuses` table, alongside the already-separate `fleet_statuses`. Seven further codes used by voyages and asset-finance deals (`draft`, `quoted`, `won`, `lost`, `pipeline`, `diligence`, `declined`) exist in no label map at all — `stTag()` renders the raw code, so the code is stored as its own label.

#### Code review found two real data bugs, both fixed before porting continued

| | Bug | Cause | Fix |
|---|---|---|---|
